# Experimental results

This folder contains the raw data behind the numbers reported in the article *On Human-Verified Specifications for LLM-Generated Microservice System Tests* (HUGS 2027) and in the master's thesis *LLM-based system tests generation from OpenAPI specifications for microservices on Kubernetes* (University of Pisa, A.Y. 2025/2026). Each run of the measurement pipeline (thesis Sec. 4.4, Fig. 4.6) has its own folder with the generated pytest suite, its execution results, the JaCoCo coverage of every service and the outcome of every mutant.

All runs use Gemini 3.1 Pro through WeaveSuite on three applications: [SockShop](https://github.com/helidon-sockshop/sockshop) and [KubePay](https://github.com/teamlead/spring-microservices-kubernetes-demo) (validation set, used to engineer the prompt) and [Lakeside Mutual](https://github.com/Microservice-API-Patterns/LakesideMutual) (held-out, never used while engineering the prompt).

## Quick start

```bash
python results/scripts/recompute_aggregates.py               # every reported mean, sd, SE, spread, normalized score
python results/scripts/recompute_aggregates.py --from-files  # same, from the summary.json of each run
python results/scripts/recompute_aggregates.py --from-raw    # same, recomputing each run from JaCoCo XML + mutants.json
```

Python 3 standard library only. The script prints each reported value next to the recomputed one. [`manifest.csv`](manifest.csv) lists every run with its values and folder.

## Experiments

| Folder | What it is | Research question |
|---|---|---|
| [`validation/`](validation) | Second phase of prompt engineering: each prompt version (v05–v30), 10 runs at temperature 0.2 on SockShop or KubePay, alternating between the two applications. Each version adds one edit to the previous one. | RQ2 — impact of system-testing principles in the prompt on suite quality |
| [`held-out/`](held-out) | The locked prompt (v30) on Lakeside Mutual, 20 runs at temperature 0.2. | RQ3 — generalization to an unseen application |
| [`temperature/`](temperature) | v30 on all three applications at temperatures 0.2–0.7, 20 runs each. The 0.2 runs of SockShop and KubePay are the 20 "locked version" runs of thesis Sec. 4.6. | RQ4 — sensitivity to the temperature |
| [`unpatched/`](unpatched) | v30 at temperature 0.2, 10 runs per application, with the raw framework-generated OpenAPI specifications instead of the human-verified (patched) ones. | RQ1 — dependence on the quality of the input specifications |

The same run is stored in two places when two tables report it (git stores identical files once): `held-out/lakeside-mutual/temp-0.2/run-NN` = `temperature/lakeside-mutual/temp-0.2/run-NN`, and `validation/kubepay/v30/run-NN` = `temperature/kubepay/temp-0.2/run-NN` for NN = 01–10. The run number in a folder name is the run number in the thesis appendix tables.

## How to read a run folder

```
run-NN/
  summary.json                 the pipeline's result for this run
  tests/generated_tests.py     the pytest suite generated by the LLM
  tests/generated_tests.json   the same tests as stored by WeaveSuite before execution (status "pending")
  execution/tests.json         each test after the baseline execution on the unmutated application
  coverage/<service>.xml       JaCoCo report of each service (instruction, line, branch, method counters)
  coverage/<service>.exec      JaCoCo execution data, to regenerate reports with jacococli and the compiled classes
  mutation/mutants.json        one entry per mutant: killed or survived, and by which tests
```

Not every folder has every file; the `availability` column of `manifest.csv` tells which runs are complete.

**summary.json**

- `test_count`, `passed_count`, `pass_rate`: tests generated and tests passing on the unmutated application.
- `coverage`: instruction coverage, i.e. covered bytecode instructions over all instructions of the measured services (`coverage_per_service._covered / _total`); `coverage_per_service.<service>` is the same ratio for one service.
- `killed`, `total_mutants`, `mutation_score`: mutants killed out of the catalogue (37 SockShop, 27 KubePay, 32 Lakeside Mutual). A mutant is killed when at least one test that passed on the original application fails against the application with that mutant deployed (thesis Sec. 4.4).
- Values are fractions (0–1); the thesis and `manifest.csv` show them as percentages.

**execution/tests.json**: `name`, `code`, `status` (`passed`/`failed`), `errorMessage` (assertion message for failing tests), `duration`, `endpoint`.

**mutation/mutants.json**: `mutant_id`, `service`, `image` (container image of the mutant), `killed`, `killing_tests` (`id`, `name`, assertion `error` of each test that killed it), `error` (deployment error, if any). The mutants are described in [`../mutants/`](../mutants) under the same IDs (e.g. `CARTS-M08`).

**Normalized mutation score** (article Fig. 2, thesis Fig. 5.1): mutation score divided by the killable upper bound, i.e. the mutants that a specification-grounded test can kill: 32 of 37 (SockShop), 24 of 27 (KubePay), 25 of 32 (Lakeside Mutual), thesis Sec. 4.5.3 and 5.1.1.

## manifest.csv

One row per run reported in the thesis: `experiment`, `application`, `prompt_version`, `temperature`, `specification` (patched/raw), `run`, `tests`, `passed`, `pass_rate`, `instruction_coverage` (%), `mutation_score` (%), `killed`, `total_mutants`, `total_instructions`, `coverage_per_service` (%), `thesis_table`, `availability`, `values_source`, `run_files_differ`, `path` (run folder), `source_folder` (original folder of the experiment workspace; its name does not always state the temperature of the runs, the `temperature` column does).

The per-run values are those of the experiment spreadsheets in [`spreadsheets/`](spreadsheets), from which the thesis tables were built; for the unpatched runs and the few runs whose thesis values are those of the run files, they are those of the run's `summary.json` (`values_source` says which). The run folders contain the outputs as produced, unchanged; `--from-files` recomputes everything from them instead.
