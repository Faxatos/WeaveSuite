# Mutants

The mutants used to measure the strength of the generated system-test suites: 37 for [SockShop](https://github.com/helidon-sockshop/sockshop), 27 for [KubePay](https://github.com/teamlead/spring-microservices-kubernetes-demo) and 32 for [Lakeside Mutual](https://github.com/Microservice-API-Patterns/LakesideMutual). Each mutant is a single fault injected into the source code of one service.

The IDs are the ones used everywhere else: in the thesis, and in `mutation/mutants.json` of every run in [`../results/`](../results), which records whether each mutant was killed and by which tests.

## How the mutants are used

Since the suites are black-box system tests talking to the services over HTTP, every mutant is built and deployed in the same way as the original service:
- **Build:** a build script applies one patch at a time and produces a container image, tagged with the mutant it carries.
- **Swap:** during mutation testing, the measurement pipeline (thesis Sec. 4.4) replaces the image of the affected service in the running deployment with the mutant image and waits for the rollout.
- **Run:** the suite is executed against the mutated deployment.
- **Verdict:** a mutant is **killed** when at least one test that passed on the original application fails against it. Afterwards the service is restored to its original image.

The operators come from the conventional catalogue of mutation operators: negating or altering a conditional, replacing a return value, removing a statement, replacing a constant, replacing an arithmetic or relational operator, swapping arguments, shifting a conditional boundary, introducing an off-by-one error and replacing a method call.

| Application | Mutants per service (thesis Table 3.2) | Total |
|---|---|---|
| SockShop | Carts 8, Orders 9, Users 7, Catalog 5, Shipping 4, Payment 4 | 37 |
| KubePay | Wallet 10, Users 8, Auth 8, Gateway 1 | 27 |
| Lakeside Mutual | Policy Management (`POLICY`) 10, Customer Core (`CORE`) 9, Customer Self-Service (`CSSB`) 9, Customer Management (`CMB`) 4 | 32 |

## Folder layout

```
<Application>/<MUTANT-ID>/
  <MUTANT-ID>.patch     the mutation as a unified diff against the application's source tree
  <File>.java           SockShop only: the complete mutated source file
```

Apply a patch with `git apply` from the root of the repository it targets, and revert it with `git apply -R`:
- **SockShop:** the repository of the service, e.g. [helidon-sockshop/carts](https://github.com/helidon-sockshop/carts) for `CARTS-*` (paths start with `carts-core/`, `orders-core/`, …).
- **KubePay and Lakeside Mutual:** the application's repository (paths start with the service module, e.g. `wallet/wallet-service/`, `policy-management-backend/`).

```bash
cd carts                                   # clone of helidon-sockshop/carts
git apply    ../WeaveSuite/mutants/SockShop/CARTS-M01/CARTS-M01.patch
git apply -R ../WeaveSuite/mutants/SockShop/CARTS-M01/CARTS-M01.patch
```

## Mutants that no specification-driven test can kill

The mutants were placed wherever an operator applies in the code, not where a black-box test can observe the effect. The thesis therefore asks two questions of each surviving mutant, following the RIPR model:
1. Can a test derived from the specification execute the mutated code?
2. Can an oracle grounded in the specification tell the corrupted output from a correct one?

A "no" to either question makes the mutant unkillable by any well-formed system test. The unkillable mutants set the upper bound used by the **normalized mutation score** (article Fig. 2, thesis Fig. 5.1).

| Application | Unkillable mutants | Why | Killable (upper bound) |
|---|---|---|---|
| SockShop (Sec. 4.5.3) | `SHIPPING-M01`–`M04` | Reachable but not revealable: they change internal rules (shipping company, tracking number, delivery date) that the specification documents only generically | 32 of 37 (86.49%) |
| | `CARTS-M08` | Reachable but not revealable: the specification does not say whether merging carts sums or replaces the quantity | |
| KubePay (Sec. 4.5.3) | `USERS-M05` | Not observable: it alters only the response of the internal service-to-service user-creation operation, which the specification does not document and whose response the auth service ignores | 24 of 27 (88.89%) |
| | `USERS-M07` | Reachable but not revealable: it sets the user's display name to the login, but the display name is randomly generated by the service and not specified | |
| | `WALLET-M02` | Reachable but not revealable: the top-up amount is not stated in the specification | |
| Lakeside Mutual (Sec. 5.1.1) | `CMB-M03`, `CMB-M04` | Unreachable: interaction logs are produced only by the chat feature (WebSocket), not by any documented REST operation | 25 of 32 (78.13%) |
| | `POLICY-M01`–`M05` | Reachable but not revealable: the risk-factor computation is internal business logic that the specification does not describe | |

In the patched runs of [`../results/`](../results), the SockShop and KubePay mutants above are killed at most once (`CARTS-M08`, `USERS-M05`, `USERS-M07`: one run each), the others never. The Lakeside Mutual ones are killed in 1 to 21 of 127 runs, almost always by end-to-end insurance-quote workflow tests (e.g. an expected `QUOTE_ACCEPTED` status missing from the history). For the two KubePay `USERS` mutants, thesis Sec. 4.5.3 gives the explanation of the mutations that thesis Table A.2 lists under those IDs; the explanations above refer to the mutations actually built (see the KubePay catalogue below).
